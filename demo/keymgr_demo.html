FRAMEWORK

Step 2: LLM-Generated Structured Specs

C1 Encoder Spec

Summary: 复位时清除 key_state_q 并将 key_state_ecc_q 初始化为安全 ECC 常数；正常操作时持续将 key_state_ecc_words_d 编码写入 key_state_ecc_q。

Guarantee: 复位完成后 key_state_q 恒为 0，key_state_ecc_q 恒为 SecdedInv7264ZeroEcc 常数；非复位状态下，每个时钟沿后 key_state_ecc_q 等于上一周期 key_state_ecc_words_d 的 SEC-DED 编码结果。

Uncertain: key_state_q 仅在 reset 分支被清零，正常操作分支未对其赋值，因此复位后 key_state_q 可能永久保持 0；需确认是否漏写正常更新逻辑。

C2 Decoder Spec

Summary: 为每一份 CDI/share/word 实例化 SECDED decoder，检测 key_state storage 的 ECC 错误并生成 ecc_errs。

Assumption: key_state_q[i][j][k] 与 key_state_ecc_q[i][j][k] 的位宽之和必须为 72 位，以匹配 prim_secded_inv_72_64_dec.data_i。

Bug relevance: 若位宽或语义不匹配，decoder 可能产生未定义错误标志，导致真实 ECC 错误被掩盖或误报，破坏存储完整性检测。

Spec total for selected chunks: 6 chunks → 10 guarantees + 7 assumptions + 8 uncertain_points.

Bug description written by Channel B: keymgr_ctrl.sv captures only the ECC slice of prim_secded_inv_72_64_enc into key_state_ecc_q. The clean implementation captures both {key_state_ecc_q, key_state_q}, keeping stored data and ECC synchronized.

Important: this is still a candidate finding. Phase3/Codex must check whether the source really has no other non-reset key_state_q writeback and whether the fault is externally visible.

FRAMEWORK

Step 7: Phase3 Codex Source Confirmation

Input: Channel B GAP finding plus keymgr RTL. Codex traces the producer/consumer path in source: key_state_d is computed for legal refreshes, the writeback block updates only key_state_ecc_q, the decoder checks {key_state_ecc_q, key_state_q}, and the resulting ECC error maps into keymgr fault status.

Final bug candidate: keymgr_bug_002, status confirmed_security_bug in diff_bug_convergence/keymgr/keymgr_bug_002/proof_result_v3.json.

Codex confirmation: the competition RTL computes new legal key-state payloads in key_state_d for root-key initialization and KMAC-driven update paths, but the only state writeback block never writes key_state_q outside reset. The ECC checker then compares fresh ECC against stale payload.

Observed witness: top-level C/Verilator witness observes keymgr state Invalid (0x6), fault_status=0x2000, KEY_ECC asserted, and a follow-on legal identity generation request fails.

FRAMEWORK

Step 8: Buggy vs Clean Comparison

Buggy: opentitan/keymgr_ctrl.sv:312

{key_state_ecc_q[i][j][k]} <=
    prim_secded_inv_72_64_enc(
        key_state_ecc_words_d[i][j][k]);

Only 8-bit ECC captured from 72-bit encoder output; 64-bit data portion is dropped.

Clean: opentitan-refs/keymgr_ctrl.sv:297

{key_state_ecc_q[i][j][k], key_state_q[i][j][k]} <=
    prim_secded_inv_72_64_enc(
        key_state_ecc_words_d[i][j][k]);

Both ECC and data are updated together; decoder sees consistent {ECC, data} pairs.

Impact chain: Encoder drops data → key_state_q stale → decoder sees new ECC + old data → false ecc_errs → FaultKeyEcc asserted → spurious fatal integrity fault.

NOTE

Takeaway

这个 demo 的讲法：semantic pairing 先选出高价值 pair；Channel B 把 pair 判断成 finding.json 中的 GAP 候选；Phase3/Codex 再追 RTL 数据流和软件可见 fault，确认它是最终 bug candidate。

一句话： Semantic AG preserves the pair that exposes stale data versus fresh ECC, while pruning noisy same-signal distractors.
